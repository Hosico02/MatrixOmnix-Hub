MatrixOmnix

把一个粗糙的 demo,变成可以交付的产品。

MatrixOmnix 不是单一工具,而是一个目标 —— demo → verified product。 当前由两个独立子系统协作完成:d2p 负责修改代码, MatrixOmnix Hub 负责观察、学习、给评判标准下决策。 如果未来某个子系统单独能闭环这件事,另一个就可以淘汰; 现在保持分离是因为各自的视角彼此校验。

两个子系统

做 · do-layer

d2p

LLM 驱动的 Python orchestrator。分析项目 → 规划任务 → 并行 Executor 改代码 → QA 生成失败用例作为永久回归门。 没有硬编码的 demo 类型探针 —— 一切由 LLM 推理。

GitHub ↗
~8k LOC Python · Claude / Codex / MiniMax
观 · observe-layer

MatrixOmnix Hub

d2p 运行的 PM + mentor 操作台。聚合多机事件, 用 5 条规则 + 每周 LLM 归纳识别标准漂移, 通过中文化 Vue 仪表板把待决事项交给人。所有规则修改需人批。

详情页 → GitHub ↗
~13k LOC TS · Hono + SQLite + Vue

闭环

  1. d2p 跑一次 productization,产生若干 finding,verdict 出 needs_repair。
  2. d2p 把 run 事件推到 Hub;Hub 累积所有项目的运行历史。
  3. Hub 的学习器扫历史,发现"反复出现的 finding 没被现有规则覆盖" → 提议加规则。
  4. 人在 Hub 仪表板点 ✓ 批准 → 新版 standards 入库。
  5. 下一次 d2p verifier 启动时从 Hub 拉到新规则,用新标准评判。

d2p 不依赖 Hub 也能跑(verifier 用本地缓存或代码 baseline 兜底); Hub 不依赖 d2p 也能启动(自己只是个空仪表板)。 松耦合,但合在一起形成数据→学习→分发的循环。

这是 v0.1 — 实验阶段

两个仓库分离 单机/小型多项目 本地优先 Hub 测试 271 通过

d2p 内部 Verifier(spec 已设计)实装后,这个闭环才真正活起来。 在此之前,Hub 可以单独运行接收事件、积累历史、跑学习器。
